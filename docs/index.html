Introduction

Scribe is a lightweight, local document navigation assistant widget. It acts as an interactive chatbot helper inside product admin consoles, reading local product documentation files and guiding users directly to their configuration screens using deep links.

Core Features

  • Local Markdown Indexing: Crawls directories recursively and parses files using front-matter yaml metadata. Excludes database dependencies or external APIs.
  • TF-IDF & Stemming Engine: Implements basic Term Frequency-Inverse Document Frequency (TF-IDF) scoring coupled with natural's PorterStemmer to align singular, plural, and related verb search terms accurately.
  • Session Cache (Context Window): Before calling the search engine, checks the last 10 Redis session messages for an exact previous answer. Cache hits skip the indexer entirely, returning the cached answer instantly. Cache is automatically invalidated on every reindex.
  • Persistent Chat History: Remembers previous conversations across page reloads using permanent localStorage session markers. Last 10 messages are restored from Redis on widget mount.
  • Prompt History Navigation: Supports Unix terminal-style Up/Down arrow key cycling through previously sent questions inside the input box.
  • Zero Authentication Overhead: Public unauthenticated endpoints let developers integrate search boxes and widgets into local dev and staging environments seamlessly.
No LLM Dependencies

Scribe is 100% deterministic and runs locally. It does not require Ollama, Python virtual environments, or external LLM connections, making it fast and lightweight.

Setup Guide

Follow these instructions to start the Scribe backend API and frontend dev instances in your workspace.

Prerequisites

  • Node.js (v18.0.0 or higher recommended)
  • Redis Server (running on default port 6379)

1. Run Redis Server

Make sure Redis is active on your local machine to handle session history caching:

redis-server --daemonize yes

2. Initialize Scribe API Backend

Navigate to the API folder, adjust Node paths if necessary, and boot up the server:

cd scribe-api
npm install
npm start

The backend console output will indicate boot-time auto-indexing progress and verify connection states:

{"level":"info","message":"Connecting to Redis at redis://localhost:6379...","timestamp":"2026-06-12T09:30:11.458Z"}
{"level":"info","message":"Redis connected successfully.","timestamp":"2026-06-12T09:30:11.502Z"}
{"level":"info","message":"Redis client ready.","timestamp":"2026-06-12T09:30:11.510Z"}
{"level":"info","message":"Auto-indexing local path on boot: /Scribe/scribe-api/data/nmail","timestamp":"2026-06-12T09:30:11.515Z"}
{"level":"info","message":"Successfully indexed 2 files with TF-IDF for application 'nmail'","timestamp":"2026-06-12T09:30:11.530Z"}
{"level":"info","message":"Scribe API running on http://localhost:8000","timestamp":"2026-06-12T09:30:11.545Z"}

3. Configure Environment

The API reads its configuration from a .env file in scribe-api/. A default file is included. Edit the values to match your environment:

# scribe-api/.env

# Server port
PORT=8000

# Redis connection URL
# Local:      redis://localhost:6379
# With auth:  redis://:yourpassword@yourhost:6379
REDIS_URL=redis://localhost:6379

# Reserved for future auth use
JWT_SECRET=change-me-in-production

4. Boot Widget Dev Server

Start the React dashboard workspace to view Scribe Widget in action:

cd scribe-widget
npm install
npm run dev -- --host 127.0.0.1 --port 3000

Open http://127.0.0.1:3000 to view the simulated client dashboard.

Document Schema

Scribe builds its search indexes by recursively scanning Markdown files and parsing YAML front-matter blocks at the beginning of each file.

Example Document

Create a Markdown file under scribe-api/data/<appCode>/<any-subfolders>/. For example: scribe-api/data/nmail/monitoring/watchdog.md:

---
title: Watchdog
application: nmail
module: monitoring
url: /watchdog
menu: Monitoring > Watchdog
keywords:
  - watchdog
  - monitoring
  - cron
  - alerts
---

# Watchdog System

Watchdog monitors system services, background processes, and active cron jobs. It sends real-time notifications when a service goes down or a scheduled cron fails.

## Features

- Service health checking and automated status reports.
- Cron monitoring with alert generation.

Front-matter Keys

title The human-readable title of the screen or feature. Displays in search headers. application Target workspace code (e.g., nmail). Must match directory node. module Logical module categorization (e.g., monitoring). url The relative deep-link path used by the React widget router to navigate users. menu The navigation menu hierarchy trail (e.g. Monitoring > Watchdog) shown in Scribe replies. keywords An array of custom query keywords utilized by the scoring engine (searched using stemmed forms).
YAML Delimiters Required

Front-matter blocks must be placed at the very top of files and enclosed between triple-dashed lines (---) with standard spacing formatting.

API Endpoints

Scribe exposes unauthenticated REST endpoints to query and manage the documentation search catalog and Redis sessions.

1. GET /api/health

Checks API server status. Used by the React widget for online/offline indicator dot.

Response:

{ "status": "ok" }

2. POST /api/reindex

Crawls the application's data folder recursively, rebuilds TF-IDF catalogs live without needing to restart Node, and automatically flushes all cached session answers for that application so users always receive fresh responses after doc changes.

Payload:

{ "application": "nmail" }

Response:

{
  "status": "success",
  "message": "Successfully indexed application documentation",
  "filesIndexed": 2
}

3. POST /api/chat

Submits a question and returns a navigation card. Implements a cache-first strategy: checks the last 10 session messages first. If the exact same question was already answered in the context window, the cached answer is returned immediately without running the indexer.

Payload:

{
  "application": "nmail",
  "sessionId": "sid_984hfsj3s",
  "question": "what is watchdog?",
  "userId": "demoUser"
}

Response:

{
  "answer": "Watchdog is available under **Monitoring > Watchdog**.\n\n### Description:\nWatchdog monitors system services, background processes...",
  "url": "/watchdog"
}

4. GET /api/session

Fetches the list of the last 10 messages (user and assistant) for a session on loading.

Query Parameters: ?application=nmail&sessionId=sid_984hfsj3s&userId=demoUser

Response:

[
  { "sender": "user", "message": "what is watchdog?", "timestamp": "2026-06-12T09:30:15.123Z" },
  { "sender": "assistant", "message": "Watchdog is available under...", "url": "/watchdog", "timestamp": "2026-06-12T09:30:15.542Z" }
]

5. DELETE /api/session

Clears cached message history from Redis and fallback in-memory databases. Called by the widget's trash icon button.

Payload:

{
  "application": "nmail",
  "sessionId": "sid_984hfsj3s",
  "userId": "demoUser"
}

Session Cache

Scribe uses a cache-first strategy for every chat query, backed by the Redis session context window. This avoids running the full TF-IDF indexer when the user asks a repeated question within the same conversation.

How It Works

User sends a question
        │
        ▼
  Load last 10 msgs from Redis (context window)
        │
        ▼
  Exact match found? (case-insensitive)
     ├─ YES → Return cached answer + url  ← indexer skipped ✓
     └─ NO  → Run indexer.queryAnswer()
                 └─ Save user + assistant msgs to Redis
                    └─ Return fresh answer

Cache Invalidation on Reindex

When POST /api/reindex is called (either manually via the admin dashboard or programmatically), all Redis session keys for that application are flushed using a non-blocking SCAN loop. This guarantees that stale cached answers are never returned after documentation changes.

Context Window Size

The context window stores a maximum of 10 messages per session (last 5 user + 5 assistant pairs). Older messages beyond this limit are automatically trimmed. Only questions within this window are eligible for a cache hit.

Session Message Schema

Each message entry stored in Redis has the following structure. The url field is only present on assistant entries where a document match was found:

{
  "sender": "assistant",
  "message": "Watchdog is available under **Monitoring > Watchdog**...",
  "url": "/watchdog",
  "timestamp": "2026-06-12T09:30:15.542Z"
}

Redis Key Pattern

Sessions are stored and flushed using the following key schema:

scribe:{application}:{userId}:{sessionId}

Examples:
  scribe:nmail:user_123:sid_a1b2c3d4e
  scribe:emacloud:demoUser:sid_9z8y7x6w5
Exact Match Only

Cache lookup is exact and case-insensitive — it does not do fuzzy or stemmed matching. This is intentional: fuzzy cache hits could return an answer for a slightly different question and mislead the user. Only byte-for-byte identical (lowercased) questions trigger a cache hit.

NLP & Stemming Engine

To avoid false matches and handle natural inputs correctly without heavy LLMs, Scribe integrates specialized classification pipelines.

1. Intent Classification

Scribe intercepts utility inputs first in indexer.js before triggering document index searches:

  • Time Queries: Searches matching what time or time is it return the system clock (e.g. The current time is 03:00 PM.).
  • Date Queries: Queries for today or date return the full local date (e.g. Today is Friday, June 12, 2026.).
  • Small-Talk: Handles standard greetings (hi, hello, hey, sup) and appreciation values (thanks, thank you) with pleasant custom conversational strings.
  • Identity Queries: Matches inputs like who are you or your name to state its role.

2. Search Matching & Relevance Scoring

If no conversational intent is recognized, Scribe scores document metadata using the following criteria:

Criteria Weight / Score Match Check Details
Exact Title +100 Exact lowercase string comparison match with document title.
Stemmed Exact Title +80 Comparison match of stemmed query tokens to stemmed title tokens.
Subtitle Match +50 Title contains query string.
Stemmed Subtitle Match +40 Stemmed title contains stemmed query string.
Keywords Match +30 (per token) Query stemmed tokens match document stemmed keyword arrays.
File Path Match +40 File path includes lowercase query term.
TF-IDF Content Match +0 to +50 Calculates stemmed term frequency scores against catalog body documents.
Noise Reduction

Common English stopwords (e.g. what, is, the, how, do) are automatically removed from search queries. If a query only contains stopwords (and isn't a small-talk intent), search yields an empty result directly, avoiding random keyword overlaps.
